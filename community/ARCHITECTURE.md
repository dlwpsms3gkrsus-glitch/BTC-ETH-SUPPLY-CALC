# CryptoFlow 커뮤니티 설계

## 1. 구현 범위와 경계

현재 구현은 정적 HTML/CSS/JavaScript로 실행되는 단일 브라우저 데모다. 게시글·댓글·카테고리·검색·정렬·신고·운영자 숨김/복원·감사 로그를 체험한다. 회원/운영자 선택은 UI 시뮬레이션이며 모든 데모 데이터는 사용자가 수정할 수 있다. 기본 저장소는 메모리이며 사용자가 체크한 경우에만 localStorage에 저장한다.

아래 서버, DB, API, 인증, 정책은 **운영 전환 제안이며 현재 구현되지 않았다**. 데모의 로컬 감사 로그는 위변조 방지 로그가 아니다. 실제 계정 생성·이메일 전송·사용자 간 데이터 공유·관리자 인증·실제 시세 연동·결제는 제공하지 않는다. 계산기 본체 및 별도 가격 수정과 기능을 분리한다.

## 2. AdSense 우선 원칙과 권장 운영 구성

제품의 1순위는 Google AdSense 승인 준비, 2순위는 꾸준한 재방문이다. [PRODUCT_PLAN.md](PRODUCT_PLAN.md)에 단계와 콘텐츠 전략을 정리한다. 현재 데모는 `noindex,nofollow`, 광고·분석 스크립트 없음, 일반 텍스트 작성(자동 링크·업로드 없음)을 유지한다. 이는 승인용 운영 페이지가 아니며 색인 차단은 인증·접근 제어나 개인정보 보호 수단이 아니다. 교육용 가이드 연결과 신고 UI는 준비 작업일 뿐 승인 요건 충족이나 승인을 보장하지 않는다.

운영 전환 시 공개 여부와 광고 게재 가능 여부를 별도 상태로 관리한다. `posts`에 `review_state`(pending/approved/rejected), `reviewed_at`, `reviewed_by`를 추가하고 댓글 변경도 페이지 검토 상태를 다시 평가한다. 기본은 광고 비활성이다. 신규 계정의 콘텐츠는 검토 대기로 보내고 운영자가 게시글과 댓글을 검토한 페이지에만 광고를 허용하는 보수적 정책을 제안한다. 미검토 댓글이 추가되면 해당 페이지 광고를 다시 비활성화한다. 광고 허용 판정은 서버에서 하고 캐시도 함께 무효화한다. 신고 발생 시 위험도가 높은 페이지는 재검토 동안 광고를 중단한다. 신고가 없다는 사실만으로 광고에 적합하다고 보지 않는다.

이 PR에는 광고 코드, 광고 검토 서버, AdSense 계정 연결·신청이 포함되지 않는다. 실제 광고 도입은 정책 검토, 사이트 승인 및 별도 배포 승인을 거쳐 진행한다.


```text
브라우저 (기존 계산기 + /community)
  → HTTPS 인증 서버 API (/api/v1)
    → PostgreSQL (비공개 네트워크, 최소 권한 DB 계정)
    → 인증 제공자 또는 검증된 서버 인증 라이브러리
    → 감사 로그 / 운영 지표 / 백업
```

공급자를 특정하지 않고 표준 HTTPS API와 PostgreSQL을 기본으로 한다. 프런트엔드는 정적 호스팅을 유지할 수 있지만 공유 데이터의 모든 변경과 비공개 조회는 서버가 처리해야 한다. GitHub Pages의 정적 파일이나 클라이언트 코드에 DB 비밀번호, 서비스 키, 운영자 목록·권한 판단 로직을 신뢰 경계로 두지 않는다. 서버와 DB 호스팅, 이메일 인증, 모니터링의 예상 월 비용·한도·리전을 비교한 뒤 별도 승인받는다. 현재 서비스 가입이나 유료 구성을 만들지 않는다.

초기 운영에서는 첨부파일·외부 이미지·HTML/Markdown 삽입을 제외하고 일반 텍스트만 지원해 공격 표면을 줄인다. 계산기 수치를 글에 붙이는 기능을 추가한다면 기준 시각과 출처를 함께 저장하고 실제 거래·투자 기능과 분리한다.

## 3. 인증과 권한

- 비회원은 공개 게시글과 공개 댓글만 조회한다. 작성·댓글·신고에는 인증된 계정이 필요하다.
- 인증은 검증된 라이브러리/제공자를 사용한다. 세션은 Secure, HttpOnly, 적절한 SameSite 쿠키로 보관하고 만료·로그아웃·강제 철회를 지원한다. 토큰을 localStorage에 보관하지 않는다.
- 서버가 세션에서 작성자 ID를 결정한다. 요청 본문의 `author_id`, `role`, `status`를 신뢰하지 않는다.
- 회원은 자신의 공개 콘텐츠만 정책에 따라 수정·삭제할 수 있다. 다른 회원의 콘텐츠, 신고자 정보, 숨김 원문, 운영 로그에 접근할 수 없다.
- 운영자는 신고 검토와 숨김·복원 권한만 가진다. 운영자 역할 부여·회수는 별도 관리자 절차와 MFA, 감사 기록을 요구한다. 데모 역할 선택기는 운영 빌드에서 제거한다.
- 모든 조회·수정에 객체 단위 권한 검사를 적용한다. 숨겨진 게시글의 댓글도 공개 API에서 제외한다. 검색·미리보기·캐시·오류 응답에 숨김 원문이 유출되지 않도록 한다.
- 쿠키 인증의 쓰기 요청에는 CSRF 방어, Origin 검증, 좁은 CORS 허용 목록을 적용한다. 출력은 텍스트로 렌더링하고 CSP를 적용한다.

## 4. PostgreSQL 데이터 모델 제안

모든 ID는 서버 발급 UUID, 시각은 UTC `timestamptz`를 사용한다. 아래는 구현할 스키마 계약이며 현재 DB 마이그레이션은 아니다.

| 테이블 | 핵심 필드 / 제약 |
| --- | --- |
| `users` | `id`, `auth_subject UNIQUE`, `display_name`, `role`(member/moderator/admin), `account_status`, `created_at`, `deleted_at`. 이메일은 인증 서비스에만 보관하거나 목적상 필요할 때 별도 제한 영역에 보관 |
| `categories` | `id`, `slug UNIQUE`(btc/eth/question/general), `name`, `sort_order` |
| `posts` | `id`, `author_id FK`, `category_id FK`, `title`, `body`, `status`(published/hidden/deleted), `created_at`, `updated_at`, `version` |
| `comments` | `id`, `post_id FK`, `author_id FK`, `body`, `status`, `created_at`, `updated_at`, `version`. 초기에는 1단계 댓글 |
| `reports` | `id`, `reporter_id FK`, `post_id FK NULL`, `comment_id FK NULL`, `reason_code`, `details`, `state`(open/reviewing/resolved/dismissed), `assigned_to`, `resolution`, `created_at`, `resolved_at`. 대상은 CHECK로 정확히 하나만 허용 |
| `moderation_actions` | `id`, `actor_id FK`, `post_id/comment_id`, `action`(hide/restore), `reason`, `before_status`, `after_status`, `report_id NULL`, `request_id`, `created_at`. 대상은 정확히 하나 |
| `audit_events` | `id`, `actor_id`, `event_type`, `target_type`, `target_id`, `request_id`, `created_at`, 최소한의 구조화된 메타데이터. 원문·토큰·비밀정보는 기록하지 않음 |

게시글 제목·본문, 댓글, 신고 설명·처리 사유에 서버/DB 길이 제약을 함께 둔다. 초기 권장치는 제목 100자, 본문 5,000자, 댓글 1,000자, 신고 설명·처리 사유 500자이며 UI와 동일한 문자 계산 규칙을 사용한다. 스키마와 실제 UI 한도가 다른 경우 출시 전에 통일한다.

인덱스: 공개 글의 `(category_id, created_at DESC, id)`, 댓글의 `(post_id, created_at, id)`, 신고의 `(state, created_at)`, 감사 로그의 `(target_type, target_id, created_at)`. 공개 검색에는 한국어 검색 품질을 확인한 `pg_trgm` 또는 별도 분석기를 사용하고 쿼리·페이지 크기를 제한한다. 동일 사용자의 동일 대상 미해결 신고는 부분 유일 인덱스 두 개로 중복 방지한다. 숨김/복원, 신고 처리, 감사 이벤트 삽입은 한 트랜잭션으로 묶는다. 동시 작업 충돌은 `version` 또는 행 잠금으로 처리한다.

## 5. API 계약 제안

| 메서드 / 경로 | 권한 및 동작 |
| --- | --- |
| `GET /api/v1/me` | 현재 세션의 공개 프로필과 권한. 비로그인 상태 구분 |
| `GET /api/v1/posts?category=&q=&sort=&cursor=` | 공개 글만 조회, 최대 50개, 안정적 커서 페이지네이션 |
| `GET /api/v1/posts/:id` | 공개 글과 공개 댓글 조회. 숨김/삭제 대상은 비회원에게 원문 비노출 |
| `POST /api/v1/posts` | 인증 회원 작성, 카테고리·텍스트 검증 |
| `PATCH/DELETE /api/v1/posts/:id` | 작성자 정책에 따른 수정/논리 삭제, 버전 충돌 검사 |
| `POST /api/v1/posts/:id/comments` | 인증 회원 작성. 숨김/삭제 게시글에는 작성 금지 |
| `PATCH/DELETE /api/v1/comments/:id` | 작성자 정책 적용 |
| `POST /api/v1/reports` | 인증 회원 신고, 정확히 하나의 대상, 사유 필수, 중복 제한 |
| `GET /api/v1/moderation/reports?state=&cursor=` | 운영자만 신고·검토에 필요한 원문 조회 |
| `POST /api/v1/moderation/posts/:id/actions` | 운영자 숨김/복원, `action`, `reason`, `expected_version` 필수 |
| `POST /api/v1/moderation/comments/:id/actions` | 댓글에 동일한 처리 |
| `PATCH /api/v1/moderation/reports/:id` | 담당자 지정, 검토/해결/기각, 결론·사유 저장 |
| `GET /api/v1/moderation/audit?cursor=` | 운영자 또는 별도 감사 권한, 개인정보 최소화 |

`401/403/404/409/422/429`를 일관되게 사용하고 내부 SQL·스택·사용자 존재 여부를 불필요하게 노출하지 않는다. 변경 요청에는 재시도용 idempotency key를 적용해 중복 제출을 방지한다. 삭제 API는 운영 정책에 따라 논리 삭제하며 영구 파기 작업과 분리한다.

## 6. 신고 처리와 운영

1. 회원이 사기·개인정보 노출·괴롭힘·스팸 등 사유로 신고한다. 신고 접수는 자동 숨김이나 제재를 의미하지 않는다.
2. 운영자는 대기열에서 담당자를 지정하고 원문과 맥락을 확인한다. 신고자 신원은 다른 회원에게 공개하지 않는다.
3. 필요하면 사유를 남겨 콘텐츠를 숨긴다. 게시글 숨김은 하위 댓글의 공개 노출도 막지만 댓글의 개별 상태를 덮어쓰지 않는다.
4. 해결/기각 결과와 사유를 기록한다. 복원할 때도 사유를 남기며 게시글 복원만으로 별도 숨김 댓글까지 복원하지 않는다.
5. 작성자에게 정책 근거와 이의 제기 경로를 제공한다. 알림 전송은 운영 단계에서 별도 구현한다. 신고 원문과 신고자 신원은 알림에 포함하지 않는다.

콘텐츠 숨김과 계정 제재는 분리한다. 운영자는 감사 로그를 수정·삭제하지 못하게 하고, DB 백업/접근 로그와 함께 독립적으로 보존한다. 동일 대상 동시 처리, 이미 처리된 신고 재시도, 복원 충돌을 테스트한다. 긴급 개인정보 노출·계정 탈취 신고의 대응 담당자와 목표 응답 시간을 출시 전에 정한다.

## 7. 개인정보·보존·남용 방지

다음은 운영 정책 초안이며 서비스 지역과 법적 의무를 검토해 확정·공지한다.

- 수집 최소화: 닉네임과 인증 식별자 중심. 지갑 비밀키·시드 문구·주민번호를 수집하지 않으며 글에 올리지 않도록 안내한다. 개인정보 처리방침, 이용 규칙, 탈퇴·삭제 요청 경로를 제공한다.
- 탈퇴: 세션을 철회하고 프로필을 비활성화한다. 작성 콘텐츠의 삭제/익명화 범위를 사전에 설명한다. 필요 보존 기록은 목적·기한·접근 권한을 제한한다.
- 보존 제안: 일반 접근 로그 30일, 처리 완료 신고와 운영 감사 기록 180일, 삭제 대기 원문 최대 30일, 암호화 백업 30일 순환. 법적 보존이 필요한 예외는 근거와 종료일을 기록한다. 백업 복구 시 삭제 이력을 다시 적용한다.
- localStorage 데모에는 자동 만료 보장이 없다. 실제 개인정보를 입력하지 않는다. 운영 전환 때 데모 데이터를 자동 업로드하지 않는다.
- 남용 방지 초기값: 계정별 글 5건/10분, 댓글 20건/10분, 신고 5건/시간. 별도 IP 제한과 전체 서비스 한도를 병행하되 공유망 오탐을 점검한다. 인증 시도에는 지수 지연과 잠금 정책을 둔다. `429`와 `Retry-After`를 반환한다.
- 본문 크기·검색 길이·페이지 크기·쿼리 시간을 제한하고 파라미터 바인딩, 스팸 탐지, URL 안전 처리, TLS, 백업 암호화를 적용한다. 원문·세션·인증 코드를 일반 애플리케이션 로그로 남기지 않는다.

## 8. 운영 출시 수용 기준

아래 항목이 충족되기 전에는 이 데모를 다중 사용자 서비스로 안내하지 않는다.

- [ ] 실제 인증, 이메일/계정 복구, 세션 만료·철회, 운영자 MFA와 역할 부여 절차 검증
- [ ] 모든 객체의 작성자/운영자 권한 검사와 IDOR·CSRF·XSS·SQL 주입 방어 테스트 통과
- [ ] 숨김 게시글·댓글이 공개 API, 검색, 캐시에서 노출되지 않음
- [ ] 두 사용자·두 운영자의 동시 작성/신고/숨김/복원 및 재시도 테스트 통과
- [ ] DB 마이그레이션·롤백, 백업 복원 훈련, 삭제 이력 재적용, 장애 알림 확인
- [ ] 신고 정책·처리 책임자·이의 제기·개인정보 처리방침·보존/파기 절차 확정
- [ ] 실제 데이터가 없는 스테이징에서 모바일·키보드·스크린리더·오류/오프라인 흐름 검증
